我的理解

由小林生成，供小涵审阅修改

这次重构的核心不是单点性能优化，而是把隐含在进程里的状态变成具有生命周期、权限和恢复语义的基础设施。真正值得复用的是升级设计原则：任何不可逆迁移都必须配套备份与修复工具；任何插件化都要同时解决来源、版本、能力和授权；任何“隐私模式”都必须明确其保护边界。

关键要点

  • 状态资源化：会话与工作区支持寻址、迁移、快照和恢复，SQLite 提供搜索与并发安全。
  • 边界收敛：Control UI 只做 Gateway 客户端，编辑器与 Changes 面板不越界替代 IDE 或 Git。
  • 插件治理：Provider 独立分发必须配套修复、迁移、版本展示及可执行来源授权。
  • 安全与恢复：按入口、凭证、执行分层，关键策略采用 fail closed；升级前备份，升级后运行 doctor 并核对路由和会话。
  • 适用场景：OpenClaw 生产部署、会话迁移、Provider 拆包和高密度 Cron 环境升级。

OpenClaw 2.0：欠下的技术债

2026 年 8 月 31 日 OpenClaw 发布 v2026.8.1（官方称 OpenClaw 2.0），合并 16000+ PR、933 位贡献者。文章重点分析架构变化及代价。

核心变化

  • 会话从进程内状态变为可寻址、可迁移、可共享、可快照、可恢复并带访问控制的资源，工作区随会话迁移。
  • 会话与 transcript 迁入 SQLite，带来搜索、并发安全和恢复能力，但升级前必须使用 openclaw backup sqlite 创建可恢复备份，回滚不是简单复制文件。
  • Control UI 退化为 Gateway 客户端，请求数从约 140 降至 45，启动从 1.6 秒降至 575 毫秒；文件编辑器和 Changes 面板明确保持边界，不取代 IDE 或 Git 客户端。
  • 官方 provider 拆为按需安装的独立包，必须配套 update repair、doctor 迁移、能力/来源/版本展示和可执行来源的显式授权。
  • 安全分为 Gateway 入口、凭证和执行三层；共享会话不是租户隔离，Incognito 只控制本地留存，消息仍会发送给模型 provider。
  • Active Memory、Grounded dreaming 和自动自学习默认开启，但支持来源追溯、显式关闭和定点删除。

可靠性与升级

反复出现的工程模式是失败时可观测、可恢复、fail closed；ask=off + askFallback=deny 无法生成 allowlist 时直接拒绝。建议先备份、openclaw doctor、升级、openclaw doctor --fix，最后检查模型路由和 SQLite 会话。Cron 密集生产环境、受影响 provider 和需要旧版会话可读的部署应先在 staging 验证。
